Measurement-specific costs include a separate Java HTTP/metrics supervisor, its full-payload proxy traffic, CPU instrumentation, per-request file logging, cgroup sampling and diagnostic JVMs. They are real costs of these results and remain in total accounting. A production service still needs containment/ownership/transport, but has not demonstrated that it needs this exact measurement implementation or its observed footprint. Conversely, neither removing it on paper nor projecting the worker's roughly 434 MiB RSS establishes production capacity. No production requirement or memory saving is quantified by subtraction.

This resolves the key interpretation ambiguity: **the unmatched historical durations/heap settings cannot establish causality or justify a larger plan**. The fixed-state experiment reveals a concrete harness/runtime accounting concern and near-cap behavior, with slowing rather than clearly endless growth over this finite window. The next bounded native validation should begin with that same hold and worker-versus-supervisor accounting; if growth continues, stop before repeated games and diagnose the specific component. No broad memory tuning or additional prompt implementation is authorized or indicated.
