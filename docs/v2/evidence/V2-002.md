## BUG-064A: two reports with different outcomes

### Surtr — confirmed P1, lookup/normalization defect

1. As guest, open `/decks/new/commander/`, search `Surtr, Fiery Jötun`, choose **Build a deck with Surtr, Fiery Jötun**.
2. Observe selected commander and printing `be38985c-f7a9-4885-9035-09390b4b754a`. Reload, then follow Sign In/Sign Up with its `save_guest=1` return and sign into a local fixture account.
3. Expected: account-save accepts the selected valid catalog card/printing and opens a saved deck. Actual: draft remains, with `Every card and printing must be resolved before the deck can be saved. Surtr, Fiery Jötun: No exact card-name match was found.`
4. Independently create a saved Kaalia fixture, add Surtr via the card input, open Surtr's action menu. Addition succeeds, but **Not a Commander** is disabled. Expected: eligible Surtr can replace commander. Actual explicit update POST also rejects it.

Backend reproduction, same local authenticated fixture, `Accept: application/json`, same-origin request:

```text
POST /decks/import/save
{"name":"M0 Surtr","format":"Commander","commander_name":"Surtr, Fiery Jötun",
 "commander_print_id":"be38985c-f7a9-4885-9035-09390b4b754a",
 "cards":[{"name":"Forest","qty":1},{"name":"Kaalia of the Vast","qty":1}]}
→ 422, unresolved ["Surtr, Fiery Jötun: No exact card-name match was found."]

POST /decks/commander (form: id=<owned fixture>, commander_name=Surtr, Fiery Jötun)
→ 400, "Could not update commander: that card is not a valid commander."
```

The extra Kaalia/Forest rows were a shared synthetic control; the browser also reproduced the failure with a commander-only Surtr draft.

Read-only local SQL evidence:

```sql
SELECT name, name_search, normalize_card_name(name), is_commander_candidate, default_print_id
FROM oracle_cards WHERE name IN ('Surtr, Fiery Jötun', 'Kaalia of the Vast');
```

| Name | Stored search / SQL normalization | Candidate | Default printing |
| --- | --- | --- | --- |
| Surtr, Fiery Jötun | `surtr fiery jotun` / `surtr fiery jotun` | true | `be38985c-f7a9-4885-9035-09390b4b754a` |
| Kaalia of the Vast | `kaalia of the vast` / `kaalia of the vast` | true | `819a21b1-ec52-4c83-85b4-491600b2e434` |

Cause is supported by the actual data and source: `cards.NormalizeName` in `internal/cards/model.go` preserves Unicode letters (`surtr fiery jötun`), but SQL `normalize_card_name` applies `unaccent` (`surtr fiery jotun`). `LookupCardsByNames` joins those unequal normalized strings directly. `buildDeckImportReview` treats that miss as unresolved; saved commander candidate/update lookup also uses the batch path. Single-card selection uses SQL-side normalization, explaining why creation search/selection and adding the card succeed. This is not a missing catalog card, illegal commander, or a reason to hard-code Surtr.

**Disposition:** required BUG-064A fix in a later task; fix shared normalization semantics, then regress accented/case/printing identities across creation, import/save, candidate lists, saved change and reload. P1 because it blocks persistence/use of a selected valid commander in a core supported flow. Scope of other accented names is source-inferred, not an exhaustive observed list.

## BUG-064B: persistence and save-state correctness

### Confirmed saved-note failure, P1

1. Open an owned synthetic saved deck, Analysis → Notes. Enter `M0 persisted note`; independently fetch its server HTML and confirm that text is present.
2. Stop **only this assignment's** local app process on port 18080 (leave PostgreSQL running), keeping the already loaded editor open.
3. Change Notes to `M0 unsaved note while server unavailable`. Allow the debounce to expire. The browser continues showing **Changes save automatically.** No failure, unsaved or recovery message appears. A local `/healthz` request confirms connection failure (curl exit 7).
4. Restart the same baseline binary/configuration, reload the editor and open Analysis. It shows **M0 persisted note**; the newer edit is lost.

Expected: failure/unsaved state is explicit and the pending edit remains recoverable. Actual: no error indication; reload discards it. This loses **new unsaved notes**, not the previously persisted deck/card list. P1 for recoverability and misleading save-state behavior in a core edit flow.

Source: `deck_show.html.tmpl` waits 140 ms for note input; the saved branch in `deck_show_guest_draft_script.html.tmpl` waits a further 180 ms. `submitSavedOverviewNow` clears pending payload before the request and silently catches rejection. Saved draft is memory-only; no unload flush/recovery journal was found for this path. `postSavedMutation`/`renderSaved` also lack a visible response-revision guard. **Stale-response overwrite and rapid-navigation races are source risks, not reproduced failures in this assignment.** Increasing write frequency alone will not repair the confirmed failure.
