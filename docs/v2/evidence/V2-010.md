A family may use Q or R depending on call path, zone and renderer preference. Do not infer optionality from a generic cancel button.

### Blocking, threading and GUI dependencies

1. [InputSyncronizedBase][wait] (upstream spelling) creates a `CountDownLatch(1)`. `showAndWait()` pushes into InputQueue then waits; `awaitLatchRelease()` asserts it is not the UI thread. `stop()` marks finished through FThreads, removes the input and releases the latch. `InputQueue.onGameOver` releases pending latches; `clearInputs()` stops inputs. Interrupts are reported, not a demonstrated application cancellation contract.
2. InputQueue is a blocking-deque stack with observer notifications and a synchronization point. InputProxy uses an atomic current input and schedules `showMessageInitial()` through `FThreads.invokeInEdtLater`. An idle/game-over queue produces `InputLockUI`. Commands must match the current input and cannot race a replaced prompt.
3. `IGuiGame` return-value calls create a second waiting path. Native `ReplyPool.get()` waits without a timeout. `cancelAll()` completes replies with null, and paused RemoteClientGuiGame methods can return null. Those are not acceptable implicit human answers for reconnect/expiry. Late replies and pending-wait cleanup need explicit experiments.
4. RemoteClientGuiGame distinguishes `send`, `syncAndSend`, `sendAndWait`, and `syncAndSendAndWait`. The `sync*` variants walk the trackable graph and require a safe game-thread boundary; self-contained timer/button messages can use the other path. Some prompt refreshes are safe while the game is parked. Do not serialize the live graph on a network/timer thread.
5. HostedMatch starts the engine through `game.getAction().invoke(...)`. **That method is not a per-game serial executor**: `ThreadUtil` uses a static cached game-thread pool and executes inline when already on a recognized game thread. `GameServerHandler` uses background dispatch; generic FThreads background calls create threads. Browser command serialization must be designed and proved, not assumed from method names.
6. A game waiting for a choice must be unblocked by a separate, validated reply/input dispatch path. Putting every reply behind that blocked game on one executor would deadlock. Conversely, allowing simultaneous arbitrary commands would race engine mutations. V2-011 must prove safe handoff at a parked input and ordered processing when the engine resumes.
7. `GuiDesktop` uses SwingUtilities/AWT and supplies `IGuiBase` resources, dispatch, images, dialogs, audio and other desktop services. The CLI avoids normal Singletons/window startup and has headless dialog guards, allowing this simulation. These guards may return defaults; they are not human prompts. Minimal proposed next path: keep the built modules and upstream controller/input machinery, supply a headless `IGuiGame` and explicit `IGuiBase`/event-dispatch integration where needed. Do not start by removing all GUI dependencies or rewriting game rules.
8. Shared FModel/StaticData, GuiBase, MyRandom and ThreadUtil state make independent sessions inside a JVM unproven. Start the next disposable proof with one game per process. The simulation's process exit is not evidence of cancellation, leak freedom, reclamation or sequential reuse.

### View privacy and unresolved questions for V2-011

`CardView.canBeShownTo(viewer)` and `canFaceDownBeShownTo(viewer)` distinguish zones, owner/controller and explicit look permissions. Battlefield visibility alone does not reveal a face-down card's identity. **The `...ToAny` overloads return true for a null/empty viewer collection**: always bind an explicit human viewer. CardView still carries underlying states, image keys and other metadata; GameView/trackable objects and event/log strings are not automatically safe public payloads. A selective projection must handle concealed identities/order, legitimate reveals and visibility revocation before data crosses into browser JSON.

The smallest next experiment is V2-011's disposable one-human/one-CPU harness using this exact pin/runtime. Prove a real keep/mulligan and one blocking GUI choice first, observing thread handoff and a player-filtered state; then expand only to the task card's priority, targeting/payment, combat, stack response, commander movement/recast and natural completion corpus. Questions to resolve there:

- Which `IGuiBase` calls need replacement versus harmless headless desktop support, and which event handler can be reused without renderer initialization? Avoid blank-player-name and lobby/audio prompts from HostedMatch setup.
- Can every required Q/R prompt be represented by current legal IDs/options without sending Java objects or reconstructing card rules? How are cancellation, empty optional choices and nested prompts distinguished?
- What executor/handoff model serializes commands while allowing latch/future replies, prevents stale/double replies, and snapshots safely? The native transport does not establish this contract.
- What exact view fields and textual events are allowed for the human, including face-down objects, library/CPU hand, temporary reveal and control changes? Source methods identify checks; no privacy fixture has passed yet.
- How does interruption/concession terminate both waiting paths and running AI work? On failure, can the worker be discarded without fabricating a game result? Capacity/cleanup measurements remain V2-012.

No current blocker prevents starting V2-011 under the review-state rule. An inability to preserve Forge authority or unblock actual human prompts would be a feasibility blocker, not permission to emulate rules in the browser.
